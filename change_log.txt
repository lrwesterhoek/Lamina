UNRELEASED (since 1.0.0)
- Standard DTFE's velocity gradient -- and the divergence, shear, vorticity and V-web built on it -- comes from the
  EXACT FACE INTEGRALS of the interpolant by default (docs/cleanup-plan.md D13, decided 2026-11-09 once P10.8's
  full-size check passed): formed in double, the same grids for every deposit (sampled, exact) and device, the
  definition PS-DTFE's mean-flow gradient uses, and conservative cell by cell. '--per-tet-gradient' (or
  DTFE_FACE_GRADIENT=0) keeps the deposit's own per-tetrahedron gradient, the route of every standard grid made before
  this date and the 2D build's only one; '--face-gradient' (or DTFE_FACE_GRADIENT=1) asks for the face route where
  it is not the default. The two routes differ by 5e-7 of the gradient rms per sub-domain at TNG100 z=0 and 512^3
  (294 of 134 M cells by more than 1e-4; the deposit's gradient is float32 on the GPU), at about a tenth of a GPU
  run's wall. run_dtfe.sh: FACE_GRADIENT empty (the default) passes nothing, 1 passes --face-gradient, 0
  --per-tet-gradient. tests/dev/bytecmp.sh pins DTFE_FACE_GRADIENT=0 so its reference set keeps comparing;
  tests/dtfe_metal_check.sh pins --per-tet-gradient in the runs that validate the kernel's gradient (and adds a coarse
  case under the face default), gpu_scalar_check.sh sets DTFE_FACE_GRADIENT=0. Under the face default the deposits --
  the CPU loops and the GPU kernels alike -- no longer accumulate the per-tetrahedron velocity gradient at all (9 of a
  velocity run's 13 deposited components; the face pass overwrote it; DTFE_FACE_CHECK=1 keeps it for its comparison),
  and the opt-in shared GPU grid (DTFE_GPU_SHARED=1, several threads depositing into one device grid) no longer adds
  the device's gradient on top of the face pass's: it had since the face route exists, a doubled gradient in every
  cell of such a run (no driver sets that knob; no production or rerun grid carries it).
- PS-DTFE's '--face-gradient' runs with '--gpu' (docs/cleanup-plan.md D17, 2026-11-09): the exact deposit on the GPU,
  the face sums from one CPU walk over the kept tetrahedra after it (psFaceWalk: the deposit loop's filter, mass and
  gradient, the GPU-deferred tetrahedra included; the units from the bound walk, so a GPU and a CPU run of one pass
  form the same face words -- tests/ps_face_gradient_check.sh P11: the mean flow's divergence and the mass flux
  divergence byte-identical to the CPU run's). Before, the option refused '--gpu'.
- The parallel (TBB) Delaunay insertion is compiled into every binary (docs/cleanup-plan.md P11.3, 2026-11-09;
  Makefile TBB_STD, default = TBB_PS) and both binaries take '--parallel-triangulation' / '--sequential-triangulation'
  (DTFE_TRIANGULATION_THREADS=N sets its thread budget, which the program otherwise divides the performance cores by
  the planned concurrency for). THE DEFAULT RULE, both binaries: the parallel insert for a tessellation of at least
  DTFE_TRIANGULATION_MIN_POINTS points (1000000) where more than one core is free for it -- measured at TNG100 z=0,
  512^3: 3.1x on the triangulation with one partition in flight (675 s -> 218 s summed over 27 partitions, +4.4 GB per
  partition in flight, which the auto-tuner budgets), nothing at the auto plan's concurrency (one core per
  tessellation), and the demo's 0.26M clustered points built 4.5x SLOWER in parallel, hence the threshold (the test
  suites' inputs are far below it). '--parallel-triangulation' forces it at any size, '--sequential-triangulation'
  keeps the sequential insert for every tessellation. The parallel insert's vertex and cell order differ run to run,
  so what is summed in walk order moves at rounding between two identical runs: the standard CPU deposits' float
  sums, the face pass's last bit (2e-7 of the values at 512^3), the vertex densities and the points (~1e-15), and
  PS-DTFE's velocity moments (4e-7 of the rms in 5% of the values); unchanged: PS-DTFE's fixed-point density and the
  GPU exact average's grids (byte-identical at 512^3). Both binaries print 'phase totals' at the end
  (wall seconds per phase summed over all threads and sub-domains: triangulation, deposit, face pass, dummy points,
  ...; src/phase_totals.h), the P11 placement work's input.
- Standard DTFE's exact average ('--exact-average', the production setting) deposits in the GRID FRAME
  (docs/cleanup-plan.md P10.8, 2026-11-09): every tetrahedron's geometry is formed relative to the corner of the full
  grid's cell holding its base vertex, in double (the vertices then narrow to the same floats in every sub-domain),
  its cells are named by their index in the full grid, its vertices take the hashed order the Monte-Carlo average
  already used (DTFE_MC_LEGACY=1 keeps CGAL's), and the CPU deposit and the --face-gradient pass form the inverse and
  the gradients in double, rounding each share once. Before, the frame was each sub-domain's lower corner in float32:
  where a corner lay in a finer binade than the sub-domain's extent, the GPU's vertices rounded by up to 1.9e-6 Mpc
  and flat tetrahedra deformed (TNG100-3-Dark z=0, 512^3, the auto 3^3 plan: a strip of 28 x planes with 65k cells of
  the velocity gradient off by more than 1e-4 of its rms, up to 1e-2), and CGAL's vertex labelling, which differs
  between the triangulations of two splits, moved every grid by ~2.5e-5 of its rms through the float gradient. Now a
  '--partition' or thread split leaves the GPU exact average's grids identical but for the last bit in ~1e-5 of the
  cells (its exact fixed-point sums have a unit per batch, so two splits round the shares to different units); the
  CPU exact average's float sums still follow its walk order (~1e-7). The change moves the exact-average grids by rounding -- 6e-8 of the rms on
  the small bytecmp runs (2e-16 in the double build) -- and nothing else: of bytecmp's 184 files only the 21 of the
  three CPU exact-average runs differ. The GPU kernels take one more per-tetrahedron buffer (the base cell, buffer
  22); the Monte-Carlo deposit passes cell 0 and its region frame, so its arithmetic and bytes are unchanged. The run's
  grid frame travels in User_options (three new fields; a program built against libDTFE must be rebuilt with it), and
  the exact average refuses a frame that does not match its region (one error line).
  tests/dtfe_face_gradient_check.sh G6 pins the split invariance on the GPU (--partition 3 3 3 against one domain,
  with FACE-CHECK on every sub-domain under the full-size bound); G4's 2^3 face difference went from 1.8e-6 to 0. At
  512^3 (TNG100-3-Dark z=0, the auto 3^3 plan against a 6^3 one) the density grids now differ in 1886 of 134 M cells
  and the velocity in 12308 of 403 M values, every one by a single float ulp (6e-12 of the field rms; before: 98% of
  the cells, 2.5e-5 of the rms, up to 7% in a cell); the face check's cells above 1e-4 on the 3^3 plan fell from
  64978 to 294 (the worst from 1.2e-2 to 5.7e-4), so --face-gradient's full-size check passes (D13's condition).

- '--face-gradient' (both binaries, 3D; docs/cleanup-plan.md P10): the velocity gradient and the fields built on it
  from exact FACE integrals of the interpolant (Gauss), by one shared geometry (src/CGAL_triangulation/face_sweep.h:
  each grid plane's section through each tetrahedron, clipped to the face squares; a half-open rule on region-frame
  coordinates so tetrahedra sharing a face in a grid plane decide it alike). Standard DTFE: the per-tetrahedron
  gradient's exact cell average by a second route (64^3 demo: 1.1e-5 of the rms at most; byte-identical at any thread
  count and after the Monte-Carlo, exact or GPU deposit; DTFE_FACE_CHECK=1 compares). PS-DTFE (the exact CPU deposit,
  --ps-volume-weighted): each cell's lower and upper face sums of the streams' velocities and count give the gradient
  of the face-averaged MEAN velocity, (S_up/N_up - S_lo/N_lo)/dx -- the quantity standard DTFE stores, conservative
  (a periodic pancake's mean divergence 5e-11 of its rms against +0.98 for the stream average), the stream average
  itself where no caustic touches the cell, and the folds' convergence as exact face differences; the stream average's
  divergence is written as '.a_velDivStreams', and the face momentum sums give the mass flux divergence
  div(sum_s rho_s v_s) as '.a_massFluxDiv' (by continuity -a d(1+delta)/dt; a drifted pancake's mass change equals
  its integrated outflow, caustic cells included, converging with the time step). Fixed-point face sums (order-free: byte-identical at any thread count
  and in slab mode), merged and checkpointed with the other accumulators; a one-cell --grid-window equals the full run's
  slice bit for bit. dtfelib's FieldSet.face_gradient / load(..., mean_field=True) read them. Tests:
  tests/face_sweep_check.sh, tests/dtfe_face_gradient_check.sh, tests/ps_face_gradient_check.sh (face_sweep_check's F2
  bound is 1e-9: the rounding of a tiny section's pieces reaches 1.4e-10 without fused multiply-adds, on CI's x86
  runner, against 3e-11 on arm64).

- The CPU exact deposits (both binaries' '--exact-average') are 4-8x faster with byte-identical outputs. Each
  cell used to clip the whole tetrahedron by its six planes; r3d applies them one at a time, so the tetrahedron is
  now clipped once per slab (x planes), each slab once per column (y planes) and each column per cell (z planes) --
  the same r3d_clip calls on the same vertices -- and the slabs, columns and cells beyond the parent piece's extent
  are skipped by r3d's own test (src/CGAL_triangulation/exact_sweep.h). The moments come from r3d's recursion
  written out for orders 1 and 2 (the same operations in the same order: bit-identical under clang; GCC builds keep
  r3d_reduce), and R3D_MAX_VERTS is 128 (a clipped tetrahedron holds at most ~40 vertices). 256^3 grid, M1 Max:
  PS-DTFE 90.2 -> 22.9 s with 2.1M particles (the sampled CPU deposit: 29.9 s) and 50.8 -> 7.9 s with 0.26M;
  standard DTFE 42.9 -> 8.1 s and 24.1 -> 3.1 s. tests/dev/bytecmp.sh now also runs the CPU exact deposits (17 runs).
- The GPU exact deposits (Metal and CUDA/HIP) no longer clip with a float32 port of r3d: they integrate each
  tetrahedron-cell intersection by a z-sweep (metal/exact_clip.metal.inc, its twin gpu_exact_clip.cuh). Between
  breakpoints in z the cross-section's moments are polynomials of degree <= 4, so 3-point Gauss-Legendre per interval
  is exact; each cross-section is the tetrahedron's quad clipped to the cell by a closed 2D Green chain. All state
  stays in registers (the r3d vertex graph spilled 832 B per thread and was latency-bound, ALUs ~1% busy). Two
  numerical rules made it robust under fast math: the Green cross term is written so a collapsed segment gives exactly
  0 even when fused into an FMA, and close breakpoints are never merged. Order-1 and order-2 volumes are bit-identical
  (the pass that sums a tet's weights and the deposit agree exactly). One partition, M1 Max, exact deposit: 0.26M
  particles at 256^3 18.1 -> 8.7 s, 2.1M at 128^3 10.8 -> 6.2 s, 2.1M at 256^3 35.7 -> 18.1 s (52 s before today's
  GPU changes); standard DTFE 0.26M at 256^3 3.7-4.9 -> 1.8-2.2 s. Against the double CPU reference it is as close as the
  port or closer (w64 at 256^3: density 1.2e-3 of rms, velDisp 2.5e-3 against 3.0e-2; tet touches and caustic classes
  nearer the CPU's). On exactly lattice-aligned tetrahedra it leaves pieces of <= 1e-7 cell in cells they only touch at
  a face (counted as tet touches; mass effect ~1e-7). The two passes of the exact items also run as separate pipelines
  (a function constant / template parameter), so the summing pass carries none of the deposit's registers.
- PS-DTFE's GPU exact deposit wrote spurious velocity dispersions (a float32 limit older than this release): each
  piece adds G^T Cov G, the variance of the tet's linear velocity over it, and on thin tets with steep velocity
  gradients that cancels far beyond float precision. TNG100-3-Dark z = 0 at 512^3: dispersions up to 5.9e10 (km/s)^2
  in ~1% of the cells, a box mean of 5415 against the CPU's 1716 (the CPU, in double: at most 1.75e6). Now a tet whose
  dispersion float32 cannot resolve to ~6e-4 (per velocity component |G|^2 ell^2 / range^2 above EX_DISP_KAPPA2) goes to
  the CPU's double exact deposit, as float-degenerate tets already did, and the rest is clamped to bounds a correct
  value always meets (each piece's mean velocity within the vertices' range, its variance at most range^2/4, the
  covariances at most the product of the half-ranges). That run: 20.6M of the tets deferred, mean and maximum equal to the CPU's (1715.8,
  1.752e6), the worst cell 2.3e-2 of the rms off (was 3.9e6), wall 17m08s -> 17m39s. Metal and CUDA/HIP.

  every PS line with a split, and 5 standard lines); the outputs of a given plan do not (tests/dev/bytecmp.sh pins
  every run's plan):
  * PS-DTFE books each partition's sub-grid as measured on the particles (psPartitionSpans: the split's largest

    leave 57.1 GB free: 53.1 GB after the 4 GB headroom"), and DTFE_MEM_FRACTION when it is set.
  * Standard DTFE's predicted peak is the larger of the loop and the post-processing, not their sum: the loop holds
    its own grids and the busiest partition; the post-processing every grid plus the share of the busiest partition
    the allocator keeps (all of it up to 1 GB, 0.35 of a larger one). Never above the old figure (256^3 with the
    production fields: 2.99 -> 2.59 GB; dtfe_auto_tune_check E now 1.08x the measured peak, from 1.57x). The SUMMARY
    prints 'before post-proc', the peak when the post-processing began, so a real run shows which phase set its peak.
  * PS-DTFE's partition loop admits partitions beyond the plan's '--max-concurrent' while memory allows (the single
    build; the double build and the float sums keep the plan's count, since their grids would follow the in-flight
    count). The plan's count is the floor. A ledger -- the free memory when the loop started, less the headroom,

    share of the point records) and the run's own growth -- must hold one partition's need for every partition in
    flight plus the new one, and the live free memory one more. Partitions enter strictly in index order, so the gate
    delays and never deadlocks. The log says "dynamic: at least the plan's m ..." (or why it did not start) and, after

  * src/config.cfg (the sample configuration) uses the new keys and no longer stops on 'sampling' (never an option).
- Behaviour change: the *_METAL_* aliases of the GPU knobs (PS_METAL_CHUNK, DTFE_METAL_TIMING, PS_METAL_FLOAT_MASS,
  PS_METAL_FLOAT_MOMENTS, DTFE_METAL_FLOAT_GRIDS, ...) are no longer read; use the *_GPU_* names.
- PS-DTFE's CPU deposit (the default single-precision build) claims its blocks of 256 cells from one shared counter,
  and its team grows as cores come free: a partition that finishes hands its core to the deposits still running
  (CorePool in src/thread_count.h). The pool also counts the CPU teams that do not ask it, for as long as they run

Phase-space DTFE (PS-DTFE)
- '--ps-vertex-mass': tetrahedron masses that do not depend on the Lagrangian chart; removes the suppressed
  density contrast when evolved initial positions are the Lagrangian input.
- '--ps-volume-weighted': velocity moments weighted by Eulerian volume, the standard-DTFE convention (the
  dispersion stays mass-weighted).
- '.hidden_streams' / '.a_hidden_streams': bit 1 marks cells that a folded tetrahedron overlaps while '.streams'
  misses it, bit 2 cells holding the mass of a tetrahedron too small for a sample.
- '--ps-exact-deposit' and '--ps-caustics' run on the GPU and in 2D. '.causticClass' classifies the folds
  (parity, collapse multiplicity, umbilic indicator); '--ps-caustic-cusps' adds A3 cusp and A4 swallowtail bits
  (CPU deposit).
- '--ps-window x0 x1 y0 y1 z0 z1' (Mpc): compute and write only a box of the full grid, equal to the full run's
  cells; with '--partition' and '--tessellation-cache', partitions that cannot reach the window are skipped.
- '--ps-alpha-shape' (non-periodic runs): drops convex-hull slivers, so a partitioned run agrees with one
  tessellation.
- '--parallel-triangulation' (TBB, opt-in): about 2.7x faster triangulation.
- '--fixed-point-merge' (opt-in): an order-free exact integer merge of the partitions (9 bytes per component and
  cell).
- Point evaluation: '--pts-lagrangian' (each stream's Lagrangian position), '--pts-scalar' with
  '--scalar-dataset', and the fold flag with '--ps-caustics'.
- PS_MASS_AUDIT=1 or 2 prints the mass bookkeeping of every pass.

Standard DTFE
- '--exact-average' runs on the GPU (6.6x the CPU for 0.26M particles at 256^3) and in 2D; on a 512^3 TNG run it
  costs 1.14-1.65x the wall time of the sampled average.
- The '--gpu' '_a' interpolation is rewritten and sums in exact fixed point: two GPU runs are byte-identical.
- Monte-Carlo cell averages ('--method 1'): samples centred on each tetrahedron's centroid, vertex order hashed
  from the positions; unbiased (box mean 1.00002 on the demo) and the same for any split.
- '--sample-points' and '--serve' work with '--partition', '--pts-vel-grad' and '--pts-scalar'.
- '--scale-factor a' for the V-web (else the snapshot's 'Time'); the T-web works in 2D.

VERSION 1.3.0
- Added exact '_a' volume averaging for the STANDARD DTFE binary, '--exact-average'
  (reuses the vendored third_party/r3d): the volume-averaged fields are computed by
  integrating the LINEAR DTFE interpolant analytically over every grid-cell/tetrahedron
  intersection instead of Monte-Carlo sampling. For a linear field the integral over each
  intersection piece is its centroid value times the piece volume, so order-1 moments
  suffice; the per-tet loop lives in interpolateGrid_averaged_1 (method-1 scatter
  topology) with the SAME cell classification as the sampled path -- the single-grid-cell
  fast path (centroid x volume) was already exact and is shared, the region window is
  clamped exactly like out-of-region samples, and the TEST_PADDING dummy-cell flagging
  covers every overlapped cell. '--samples' is ignored; '--method 2/3' is rejected with a
  clear error (the exact average replaces the sampled estimate); MY_SCALAR builds reject
  the flag (a user-defined scalar is not linear inside a tet); with '--gpu' the
  interpolation falls back to the CPU with a warning; 3D only. Measured: on a PERFECT
  periodic lattice every '.a_den' cell is 1 to float rounding (max |v-1| = 1.8e-7), and
  the sampled method-1 density approaches the exact grid monotonically (pancake, grid 64:
  L1 = 4.6e-2 / 1.1e-2 / 1.9e-3 at --samples 100/1000/10000). Two gated tests added to
  tests/run_tests.py (suite is now 15; they skip cleanly on binaries without the flag).
  All outputs without the flag are byte-identical (A/B verified for both binaries).
- Added the exact conservative PS-DTFE deposit, '--ps-exact-deposit' (Powell & Abel 2015,
  arXiv:1412.4941), backed by the newly VENDORED third_party/r3d (r3d.c/r3d.h at upstream
  commit 58dfbfb, LANL license and citation request preserved; r3d-config.h stands in for
  the CMake-generated header; compiled once per object dir as plain C99 with -fPIC and
  linked into both binaries and libDTFE). Instead of nSub^3 sub-sampling, every kept
  tetrahedron is analytically clipped against each grid cell in its bbox window (vertex-0
  relative frame, the same affine convention as velGrad/denGrad; raw-index window with
  modulo wrapping on write, exactly like the sampled deposit) and one order-2 r3d_reduce
  per intersection yields: exact per-cell mass shares (renormalized per tet over the
  in-window volume, so conservation matches the sampled path's semantics and lands at or
  below its float floor -- measured 2.2e-10 vs 2.4e-9 on the pancake); the exact mean of
  the linear velocity profile for the velocity moment; and the piece's exact velocity
  covariance for the dispersion (intra-cell variance without sampling). '--ps-linear-
  deposit' composes by integrating the linear density profile exactly (order-1 moments,
  renormalized per tet). Folded (negative-parity) tets are handed to r3d with two vertices
  swapped. nSub is ignored -- the exact deposit is the nSub->infinity limit, '.den' ==
  '.a_den' bit-exact, and the sampled '.a_den' converges to the exact grid monotonically
  (L1 0.319/0.062/0.060 at nSub 1/3/5 on the pancake). '.streams' counts every tet with a
  nonzero intersection (integer -> bit-exact across same-split partition/thread schedules;
  serial-vs-partitioned keeps the known pre-existing FP framing edge, a handful of +-1
  cells). Released tets (--ps-halo-release) fall through to the monolithic centroid path;
  --ps-caustics orientation bits are set per intersected cell. CPU-only, 3D-only: with
  '--ps-gpu' the deposit falls back to the CPU with a warning; point evaluation is
  unaffected. Honest cost (pancake 32^3 particles / 64^3 grid, one thread): the unaveraged
  deposit is ~35x the sampled nSub=1 pass (6.7 s vs 0.19 s); the '_a' pass costs about the
  SAME as nSub=3 sampling (6.5 s vs 6.1 s) after skipping the sub-sample window expansion
  (pointless for exact clipping) -- an accuracy option, not a speed option. Validated by

- Added the PS-DTFE mass-weighted velocity DISPERSION, the signature phase-space observable for void work ('--field dispersion' / 'dispersion_a'). It is the full symmetric tensor sigma_ij = sum(rho_s (v_s,i-<v>_i)(v_s,j-<v>_j))/sum(rho_s) = <v_i v_j>-<v_i><v_j>, accumulated as the density-weighted second moment in the same cell scatter as the velocity. Writes the trace sigma^2 (the velocity "temperature") to "<output>.velDisp" and the full tensor (upper-triangle row-major, 6 components in 3D) to "<output>.velDispTensor", plus their '_a' volume-averaged versions. ~0 in cold single-stream regions (void interiors), large in multi-stream regions (walls/filaments). Validated on the Zel'dovich pancake against the analytic three-stream dispersion: slab-centre sigma^2 matches to ~0.2% and single-stream cells are 0 -- now a tracked check in tests/ps_regression_test.py. Diagonal components (variances) are clamped >=0. Correct in both the serial and '--partition' paths.
- Added a PS-DTFE vs standard-DTFE single-stream cross-check, tests/ps_standard_cross_check.py: runs both codes on the same pancake and compares where streams==1. The velocity matches tightly (~4e-6 median rel) -- both interpolate the same particle velocities linearly, so the result is nearly tessellation-independent in single-stream regions -- while the density matches only to estimator accuracy (~7% profile): density ~ 1/volume is sensitive to simplex shape and the two tessellations differ (regular Lagrangian vs stretched Eulerian), with standard DTFE additionally contaminated near the caustic. The two also use different density normalizations (standard ~mean 1, PS physical N*m/L^3), so densities are compared after dividing by their own mean.

Uses the no-partition path (the partition path adds a small partition-boundary floor that would mask the trend). The multi-stream FRACTION, by contrast, is grid-discretisation-limited (set by which cells fall in the slab), not particle-limited -- documented rather than convergence-tested.
- Implemented the per-partition sub-grid memory optimisation. Each partition now allocates only the Eulerian bounding box of the grid cells it touches, not the whole grid: a cheap first pass over the kept cells (same filtering/bounding box as the scatter) marks, per axis, which grid planes are overlapped, giving a box [subOrigin, subOrigin+subDims); axes whose touched set reaches both ends (a fold or periodic wrap) stay full. The per-partition interpolation fills this box (Quantities::ps_subOrigin/ps_subDims), and the new Quantities::addFromSubgrid maps it back into the full shared grid. On the pancake a half-box partition occupies ~15% of the grid; measured peak RSS dropped ~2.6x (4.16 -> 1.58 GB at grid 192^3, --partition 2 2 2, 8 threads) with output verified BIT-IDENTICAL to the full-grid path (1-thread, all fields). - Fixed the non-periodic path -- a finite particle cloud in vacuum now conserves mass (~0.96-1.02 across grids, was ~0.20). Two causes were addressed: (1) the density normalization used the BOX volume (N*m/L^3), but the PS vertex density is avgDensity*V_Lag/V_Eul, so for a cloud filling a fraction f of the box the mass came out a factor f too low; for a non-periodic isolated cloud (no --periodic, no --region) avgDensity is now the cloud's LAGRANGIAN mean N*m/V_lagBox (exact for a regular IC grid, where the Lagrangian bounding box is the tessellated convex hull). (2) the convex-hull boundary cells were culled as a periodic artefact; for non-periodic they are now KEPT, with a constant density from their own |det(Lagrangian edges)|/|det(Eulerian edges)| volume ratio, recovering the cloud's surface layer. The periodic path is unchanged (the cull still applies; regression/parallel/3D/smoke bit-for-bit identical). Validated by tests/ps_nonperiodic_test.py. Caveat: assumes a roughly convex, regular Lagrangian distribution (standard DTFE convex-hull assumption); feeding periodic data without --periodic is still wrong.
- Implemented CGAL TBB parallel triangulation as an OPT-IN build, `make PS-DTFE TBB=1` (or DTFE TBB=1): the single global tessellation (the no-`--partition` path) is built with CGAL's parallel insertion -- a Parallel_tag triangulation data structure, a Spatial_lock_grid lock structure, and a range insert of (point, info) pairs that runs insert_with_info under tbb::parallel_for. Gated behind -DPARALLEL_TRIANGULATION so the default builds are byte-for-byte unchanged (the sequential path moved into an #else; verified the full suite still passes without TBB). Requires `brew install tbb`. Output verified correct (the Delaunay triangulation is unique, so the regression test passes with the TBB build).
  HOWEVER -- benchmarking shows it is ~2x SLOWER than the sequential build at tested scales (1.48M pts: 5.2s seq vs ~10-13s parallel; 3.5M pts: 12.5s vs 25.3s), the gap not closing with N. Two reasons: the parallel path cannot use CGAL::Fast_location (a sequential point-location hierarchy) which the sequential build relies on, and CGAL's parallel insertion overhead (lock-grid contention on the grid-structured + periodic-copy point distribution) outweighs the ~3x core utilisation it achieves. CGAL parallel Delaunay is tuned for much larger, more uniform point sets (tens of millions+); at PS-DTFE's scales and distribution it does not pay off. The '--partition' path remains the recommended parallelisation (it parallelises BOTH the triangulation and the interpolation per partition, ~6.3x at 8 cores). Kept as an honest, opt-in option for the very-large-N many-core regime.

- Added '--avg-subsamples N' (PS-DTFE only, default 3): the linear sub-sample count nSub for the volume-averaged ('_a') fields. Each grid cell is volume-averaged over an nSub^NO_DIM regular sub-grid, and that averaged interpolation pass is the DOMINANT runtime cost of a PS-DTFE run (it iterates every Delaunay cell against nSub^3 sub-points per grid cell). Previously nSub was hardcoded to 3 (27 sub-points) in triangulation.cpp. Measured on the small parallel-check snapshot the averaged pass scales as nSub^3: nSub=3 -> 6.71 s, nSub=2 -> 2.15 s (8 sub-points, ~3.1x faster), nSub=1 -> 0.14 s (cell-centre only = the unaveraged value). Lower nSub trades a small amount of mass capture in PARTIALLY-COVERED cells (fewer sub-points sample less of a cell the tessellation only partly fills) for a large speedup; at production resolution (grid <= particle count) most cells are well covered so the difference is small -- check the printed 'density_a grid_mass/expected' stays near 1. VERSION 1.2
Added some new features:
- added code for reading data from an HDF5 Gadget file

- added a new option called '--input' or '-i' that can be used to specify the input file type, the data to read from the input file and for what species. The '--input' option has the form: '--input  input_file_type   data_to_read    particle_species_to_read'   where the last two make sense only for Gadget files. The DEFAULT values are: '--input 101 7 2'
- the new option '--input' or '-i' needs to be followed by an integer specifying the input file type. By default it understands the following options: 
      101 - gadget binary snapshot saved as single or multiple files type I or II [ DEFAULT choice unsless specified otherwise in the Makefile ]
      105 - gadget HDF5 file/files
      111 - reads particles positions and masses (weights) from a text file. First line gives particle number followed by 6 coordinates giving the box dimensions: "xMin xMax yMin yMax zMin zMax". After this each row 'i' in the file gives positions X, Y, Z and weight for particle 'i'.
      112 - reads particles positions from a text file. First line gives particle number followed by 6 coordinates giving the box dimensions: "xMin xMax yMin yMax zMin zMax". After this each row 'i' in the file gives positions X, Y and Z for particle 'i'. (note that each particle is assumed to have the same mass/weight)
      121 - read particle positions, mass and velocities from a binary file. Modify this function in file 'src/io/binary_io.cc'
      131 - read particle positions, mass and velocities from your custom file. Modify this function in file 'src/io/my_io.cc'
you can set the default output file in the Makefile by changing the values assigned to the '-DINPUT_FILE_DEFAULT' option.
- added a second integer value to the '--input' option to specify what which data to read. At the moment works only for gadget files and you can select to read the following:
      1 - read particle positions
      2 - read particle weights
      4 - read particle velocities
to read multiple data add the number corresponding to each data set, for example 3=1+2 - specifies to read only particle positions and weights/masses, while a value of 7=1+2+4 specifies to read positions, weights and velocities [ DEFAULT = 7 -read positions, weights and velocities ]
- added an additional third option after for the '--input' parameter which specifies for which gadget particle species to read the data. You can select the following:
      1 - read the data for gadget species 1 (normally gas particles)
      2 - read the data for gadget species 2 (normally dark matter particles) [DEFAULT]
      4 - read the data for gadget species 3 (usually stars or different mass DM particles in multiple resolution simulations)
      8 - read the data for gadget species 4
      16 - read the data for gadget species 5
      32 - read the data for gadget species 6
to read data for multiple species just add the number corresponding to each particle type, for example 7=1+2+4 - specifies to read the data for both particle types 1, 2 and 3.

- added the '--output' or '-o' option to specify the output file type. Available options:
      101 - the default binary output
      100 - binary file with my own custom header and file structure
you can set the default output file in the Makefile by changing the values assigned to the '-DOUTPUT_FILE_DEFAULT' option.

- added option '--resdhiftSpace' that can be used to tranform the particle positions from position-space to redshift-space. For the option to work you need to enable the '-DREDSHIFT_SPACE' option in the Makefile. Than you need to call the '--resdhiftSpace d1 d2 d3' during runtime with (d1,d2,d3) the direction along which to use the velocity for the transformation to redshift space. The (d1,d2,d3) direction will be normalized to a unit vector by the program!
