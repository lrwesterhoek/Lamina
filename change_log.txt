- RUN MODES: '--run-mode gentle|balanced|performance' in both binaries (every build; docs/cleanup-plan.md P13, the
  owner's request of 2026-11-09, designed and decided 2026-11-10) says how hard a run may lean on the machine. The
  resolution, first match wins: the flag (exact lower case; a second one is refused); the new environment variable
  DTFE_RUN_MODE, read by both binaries and the three drivers (any case; unset, empty or 'auto' = not given; any other
  word is an error); otherwise performance, the binaries' default, which is the behaviour of 2f428bc. What a mode
  sets: the thread budget (N0 = the OpenMP default; base = the performance cores on Apple silicon, else N0; gentle
  max(1, base/2), balanced base less round(base/4) clamped to 1-4, performance N0: 4 / 6 / 10 threads on an M1 Max),
  set once before any thread exists and read wherever a thread team is sized (src/run_mode.h; the look-ahead thread
  adopts it), so the auto-tuners plan for it; on Linux gentle runs at nice 10 (never lowered; macOS gets no priority
  change); the GPU's command buffers aim at 50 ms in gentle and balanced and 250 ms in performance, with 8 ms gaps in
  every mode, and an escalated pace eases back to that base (the line ends '(the default)' or '(the run mode's)');
  PS-DTFE's exact deposit puts at most 500k items in a GPU buffer in gentle and balanced and 4M in performance (no
  byte changes). An explicit lever beats the mode: OMP_NUM_THREADS keeps its thread count, the DTFE_*_THREADS pins
  keep their teams, a '--max-concurrent' above the mode's threads raises them, and '--partition', DTFE_GPU and
  '--gpu-share' stay as given; the memory budget, the estimator, the fields and the merge are not the mode's.
  PS-DTFE's new '--gpu-share auto|<fraction>' (default 1: every partition on the GPU, as before) deposits that share
  of a partitioned '--gpu' run's exact-deposit partitions on the GPU and the others on the free CPU cores at the same
  time, chosen by partition index alone; 'auto' is the run mode's share: in performance 50 round(20/(1 + 0.09
  (N0 - 1.8))) per mille within [500, 1000], 0.6 at 10 threads (DTFE_GPU_SHARE_RHO replaces the 0.09), and 1 in gentle
  and balanced, in the double build, under the float-sum variants or DTFE_MASS_AUDIT, below DTFE_AUTO_MINN particles
  and under 4 threads. A number that does not apply (without '--gpu', the sampled deposit, a CPU-only build, one
  domain) is ignored with one note, and anything but 'auto' or a fraction from 0 to 1 is refused ('600' too). A mixed

VERSION 1.0.0 (Lamina, 2026-10-23)
The project is now called Lamina (Linear Adaptive Multi-stream Interpolation for N-body Analysis): the standard
DTFE program './DTFE', the phase-space DTFE './PS-DTFE' (after Feldbrugge 2024), the Python package dtfelib and a
graphical launcher. The programs and dtfelib keep their names. Version numbers restart at 1.0.0: the entries
below are the DTFE versions Lamina continues (1.3.0 = the phase-space work up to 2026-07-12, never tagged; 1.2.2
and older = the public DTFE of Cautun & van de Weygaert 2011). Changes since 1.3.0:

Upgrading from the 1.3.0 code
- Removed options: '--metal' and '--ps-metal' (use '--gpu' / '--ps-gpu').
- The shell scripts moved from the repository root to scripts/ (config.sh, install.sh, install_dependencies.sh,
  download_snapshots.sh, run_dtfe.sh, run_ps_dtfe.sh); documentation/ is now docs/.
- No default data root and no default simulation: DTFE_DATA_ROOT names the folder that holds the simulations (a
  driver's '-d' names a simulation's own folder instead), and every run names its simulation ('-s' or DTFE_SIM,
  the plot scripts' '--sim', the pipeline's SIMS). The drivers stop with exit status 2 without them.
  dtfelib.DATA_ROOT is gone: use dtfelib.cli.require_data_root().
- Refused now, where they used to crash or give wrong grids: 'dispersion' / 'dispersion_a' in './DTFE' (they are
  PS-DTFE fields); 'velocityStd_a' in './DTFE' except with '--method 2'; '--partNo', '--region' and '--regionMpc'

  programs (it was never implemented and ran as a silent no-op). Other combinations that cannot work are refused

- Changed defaults: PS-DTFE merges its partitions in index order (bit-reproducible; '--completion-order-merge' is
  the old order); partitions are padded in Lagrangian space ('--ps-lag-padding 8'; 0 = the old Eulerian rule);
  an explicit '--partition 1' keeps one tessellation. The drivers use the GPU when the binary has one;
  run_dtfe.sh writes eight fields (T-web and V-web included) with exact cell averages and padding 15;
  run_ps_dtfe.sh writes nine fields with vertex masses, volume-weighted velocity moments and caustic flags.

  * standard-DTFE Monte-Carlo '_a' averages are unbiased and independent of the split, threads and padding (they
    lost 0.17-0.29% of the mass); DTFE_MC_LEGACY=1 restores the old sampling;
  * '.caustic' is the exact geometric fold flag (the old per-sample flag marked 21.0% of the cells of a

    old values);

    one axis: rerun them.

Phase-space DTFE (PS-DTFE)
- '--ps-vertex-mass': tetrahedron masses that do not depend on the Lagrangian chart; removes the suppressed
  density contrast when evolved initial positions are the Lagrangian input.
- '--ps-volume-weighted': velocity moments weighted by Eulerian volume, the standard-DTFE convention (the
  dispersion stays mass-weighted).
- '.hidden_streams' / '.a_hidden_streams': bit 1 marks cells that a folded tetrahedron overlaps while '.streams'
  misses it, bit 2 cells holding the mass of a tetrahedron too small for a sample.
- '--ps-exact-deposit' and '--ps-caustics' run on the GPU and in 2D. '.causticClass' classifies the folds
  (parity, collapse multiplicity, umbilic indicator); '--ps-caustic-cusps' adds A3 cusp and A4 swallowtail bits
  (CPU deposit).
- '--ps-window x0 x1 y0 y1 z0 z1' (Mpc): compute and write only a box of the full grid, equal to the full run's
  cells; with '--partition' and '--tessellation-cache', partitions that cannot reach the window are skipped.
- '--ps-alpha-shape' (non-periodic runs): drops convex-hull slivers, so a partitioned run agrees with one
  tessellation.
- '--parallel-triangulation' (TBB, opt-in): about 2.7x faster triangulation.
- '--fixed-point-merge' (opt-in): an order-free exact integer merge of the partitions (9 bytes per component and
  cell).
- Point evaluation: '--pts-lagrangian' (each stream's Lagrangian position), '--pts-scalar' with
  '--scalar-dataset', and the fold flag with '--ps-caustics'.
- PS_MASS_AUDIT=1 or 2 prints the mass bookkeeping of every pass.

Standard DTFE
- '--exact-average' runs on the GPU (6.6x the CPU for 0.26M particles at 256^3) and in 2D; on a 512^3 TNG run it
  costs 1.14-1.65x the wall time of the sampled average.
- The '--gpu' '_a' interpolation is rewritten and sums in exact fixed point: two GPU runs are byte-identical.
- Monte-Carlo cell averages ('--method 1'): samples centred on each tetrahedron's centroid, vertex order hashed
  from the positions; unbiased (box mean 1.00002 on the demo) and the same for any split.
- '--sample-points' and '--serve' work with '--partition', '--pts-vel-grad' and '--pts-scalar'.
- '--scale-factor a' for the V-web (else the snapshot's 'Time'); the T-web works in 2D.

Both programs
- 'make DOUBLE=1' builds DTFE-double / PS-DTFE-double (float64 grids, about twice the memory); 'make DIM=2'
  builds DTFE-2d / PS-DTFE-2d for 2D snapshots (CPU only). All sets coexist with the single 3D pair; a snapshot
  with the wrong number of coordinate columns is refused with the name of the binary to use.
- GPU backends METAL=1 (Apple Silicon), CUDA=1 and HIP=1, one per build; '--gpu' / '--ps-gpu' at run time, and
  the CPU with a warning when no device works. CUDA and HIP are line-by-line ports of the Metal kernels,
  compile-tested and validated through the CPU emulation (CUDAEMU=1, warp widths 32 and 64); they have not yet
  run on NVIDIA or AMD hardware.
- GPU robustness: paced command buffers, periodic grid snapshots and cause-aware retries; a chunk that keeps
  failing runs on the CPU, and the log counts the retries by cause and the passes that fell back.
- Exact sums: the PS mass and moment grids (GPU and CPU) and the standard '_a' GPU grids are 64-bit fixed-point
  sums, so PS grids are identical run to run at any thread count and '--max-concurrent'.

  than the other programs leave free less 4 GB (DTFE_MEM_FRACTION, DTFE_MEM_BUDGET_GB); a time-aware split below
  2e6 particles; a partition waits until the free memory holds it; grids above 2^32 cells. '--auto-tune-report'

- '--tessellation-cache DIR': later runs on the same input reuse the tessellation (compressed, about 0.15 KB per
  vertex); a changed input is a miss, never a wrong result.
- '--resume': a killed partitioned run continues from <prefix>.runlog.checkpoint, byte-identical to an
  uninterrupted run (the drivers pass it themselves).
- The next partition is tessellated while the GPU deposits ('--no-overlap' / '--ps-no-overlap' switch it off).
- '--serve' ('--serve-progress', '--serve-resident N'): an interactive tessellation server for Python
  (dtfelib.Estimator); a composite of partitions on disk serves boxes too large for the memory; 2D too.
- '--pts-vel-grad' writes the velocity gradient at the sample points.
- Exact point location (CGAL predicates with simulation of simplicity): a point on a shared face, edge or vertex

- '--interlace' also works without '--periodic', on a region at least half a cell inside the box.
- Environment variables follow one rule (empty = unset; 0, false, no, off switch off; 'auto' where a knob has
  three states), listed in one README table; the *_GPU_* names are primary, the *_METAL_* spellings aliases.
- '--version' and the run log's 'Build:' line give the git revision and the build time.

- Added exact '_a' volume averaging for the STANDARD DTFE binary, '--exact-average'
  (reuses the vendored third_party/r3d): the volume-averaged fields are computed by
  integrating the LINEAR DTFE interpolant analytically over every grid-cell/tetrahedron
  intersection instead of Monte-Carlo sampling. For a linear field the integral over each
  intersection piece is its centroid value times the piece volume, so order-1 moments
  suffice; the per-tet loop lives in interpolateGrid_averaged_1 (method-1 scatter
  topology) with the SAME cell classification as the sampled path -- the single-grid-cell
  fast path (centroid x volume) was already exact and is shared, the region window is
  clamped exactly like out-of-region samples, and the TEST_PADDING dummy-cell flagging
  covers every overlapped cell. '--samples' is ignored; '--method 2/3' is rejected with a
  clear error (the exact average replaces the sampled estimate); MY_SCALAR builds reject
  the flag (a user-defined scalar is not linear inside a tet); with '--gpu' the
  interpolation falls back to the CPU with a warning; 3D only. Measured: on a PERFECT
  periodic lattice every '.a_den' cell is 1 to float rounding (max |v-1| = 1.8e-7), and
  the sampled method-1 density approaches the exact grid monotonically (pancake, grid 64:
  L1 = 4.6e-2 / 1.1e-2 / 1.9e-3 at --samples 100/1000/10000). Two gated tests added to
  tests/run_tests.py (suite is now 15; they skip cleanly on binaries without the flag).
  All outputs without the flag are byte-identical (A/B verified for both binaries).
- Added the exact conservative PS-DTFE deposit, '--ps-exact-deposit' (Powell & Abel 2015,
  arXiv:1412.4941), backed by the newly VENDORED third_party/r3d (r3d.c/r3d.h at upstream
  commit 58dfbfb, LANL license and citation request preserved; r3d-config.h stands in for
  the CMake-generated header; compiled once per object dir as plain C99 with -fPIC and
  linked into both binaries and libDTFE). Instead of nSub^3 sub-sampling, every kept
  tetrahedron is analytically clipped against each grid cell in its bbox window (vertex-0
  relative frame, the same affine convention as velGrad/denGrad; raw-index window with
  modulo wrapping on write, exactly like the sampled deposit) and one order-2 r3d_reduce
  per intersection yields: exact per-cell mass shares (renormalized per tet over the
  in-window volume, so conservation matches the sampled path's semantics and lands at or
  below its float floor -- measured 2.2e-10 vs 2.4e-9 on the pancake); the exact mean of
  the linear velocity profile for the velocity moment; and the piece's exact velocity
  covariance for the dispersion (intra-cell variance without sampling). '--ps-linear-
  deposit' composes by integrating the linear density profile exactly (order-1 moments,
  renormalized per tet). Folded (negative-parity) tets are handed to r3d with two vertices
  swapped. nSub is ignored -- the exact deposit is the nSub->infinity limit, '.den' ==
  '.a_den' bit-exact, and the sampled '.a_den' converges to the exact grid monotonically
  (L1 0.319/0.062/0.060 at nSub 1/3/5 on the pancake). '.streams' counts every tet with a
  nonzero intersection (integer -> bit-exact across same-split partition/thread schedules;
  serial-vs-partitioned keeps the known pre-existing FP framing edge, a handful of +-1
  cells). Released tets (--ps-halo-release) fall through to the monolithic centroid path;
  --ps-caustics orientation bits are set per intersected cell. CPU-only, 3D-only: with
  '--ps-gpu' the deposit falls back to the CPU with a warning; point evaluation is
  unaffected. Honest cost (pancake 32^3 particles / 64^3 grid, one thread): the unaveraged
  deposit is ~35x the sampled nSub=1 pass (6.7 s vs 0.19 s); the '_a' pass costs about the
  SAME as nSub=3 sampling (6.5 s vs 6.1 s) after skipping the sub-sample window expansion

  the new gated section (D) of tests/ps_linear_deposit_check.sh (8 checks; skipped cleanly

- Added the PS-DTFE halo-interior release, '--ps-halo-release <D>' (Stuecker et al. 2021,
  arXiv:2109.09760): during the grid deposit, any kept tetrahedron whose geometric stream
  density rho_geo/rho_bar = V_lag/V_eul exceeds D is deposited MONOLITHICALLY at its
  Eulerian centroid cell -- the pre-existing mass-conserving fallback for sub-sample-spacing
  tets, now driven by zero-tripping the PASS-1 sample window -- instead of being rasterized
  over its bbox with nSub^3 sampling; the velocity/dispersion moments carry the
  centroid-evaluated velocity. The criterion is exact and local: |det Lag| > D*|det Ax| (the
  1/6 factors cancel), classified in double precision identically by the CPU and GPU
  deposits (partition protocol); the GPU path skips released tets during tet extraction and
  applies their single-cell centroid deposits host-side after the GPU grids are copied back
  (identical released counts asserted). Mass conservation is EXACT (grid mean bit-unchanged
  vs the base deposit) and cells that are single-stream in the base run keep bit-identical
  .den/.vel/.streams -- released tets live in multi-stream regions by construction. Point
  evaluation ('--sample-points') is NOT affected by this flag. Rationale: inside virialized
  halos fold counts explode (TNG50-3-Dark z=0: mean 15.6 streams/cell, max 1.9e6, 2.1e9
  tet-cell overlaps) while the sheet estimate is unconverged there anyway; the release cuts
  exactly that cost. MEASURED on TNG50-4-Dark z=0 (2e7 particles, grid 512, single-domain,
  max 383k streams in one cell): D=100/300/1000 release 13.1M/7.7M/3.6M of ~118M tets, box
  mean bit-unchanged, and only 244/22/1 cells of the 114M single-stream cells change --
  those are thin VOID-WALL sheets (stream compression rho_geo > D at cell-averaged density
  ~0.2) whose mass collapses to the centroid cell (up to ~50x locally at D=100), so the
  RECOMMENDED default is D ~ 1000 for void-focused analyses. Wall-time, honestly: the
  measured savings at THIS scale are small everywhere -- CPU nSub=1 deposit 651 -> 638 s
  at D=100 (released tets are sub-cell and already took the centroid fallback), Metal GPU
  110 -> 104 s (unaveraged) and 2305 -> 2287 s (nSub=3 '_a') -- because the deposit cost
  is dominated by mid-size tetrahedra no reasonable D releases (the CPU nSub=3 '_a' pass
  is hours at 512^3 with or without the flag; use the GPU deposit or --avg-subsamples 1
  there). The fold-count explosion the flag targets (TNG50-3-Dark: 1.9e6 streams/cell,
  2.1e9 overlaps) grows much faster than the tet count, so the flag is primarily the
  physically-motivated release of unconverged sheet regions, with speedups expected at
  those larger scales. Validated by the new tests/ps_halo_release_check.sh (pancake +
  --crossed-waves: releases happen and change the multi-stream deposit, means bit-unchanged,
  single-stream volume bit-identical, partitioned runs thread-invariant, GPU parity;
  documents that serial-vs-partitioned keeps the KNOWN pre-existing +-1-stream
  centroid-cell edge at periodic faces, which this flag neither causes nor worsens). All
  outputs without the flag are byte-identical (A/B verified for both binaries).

- Added '--avg-subsamples N' (PS-DTFE only, default 3): the linear sub-sample count nSub for the volume-averaged ('_a') fields. Each grid cell is volume-averaged over an nSub^NO_DIM regular sub-grid, and that averaged interpolation pass is the DOMINANT runtime cost of a PS-DTFE run (it iterates every Delaunay cell against nSub^3 sub-points per grid cell). Previously nSub was hardcoded to 3 (27 sub-points) in triangulation.cpp. Measured on the small parallel-check snapshot the averaged pass scales as nSub^3: nSub=3 -> 6.71 s, nSub=2 -> 2.15 s (8 sub-points, ~3.1x faster), nSub=1 -> 0.14 s (cell-centre only = the unaveraged value). Lower nSub trades a small amount of mass capture in PARTIALLY-COVERED cells (fewer sub-points sample less of a cell the tessellation only partly fills) for a large speedup; at production resolution (grid <= particle count) most cells are well covered so the difference is small -- check the printed 'density_a grid_mass/expected' stays near 1. Default 3 keeps existing behaviour/baselines unchanged (the regression and parallel tests, which don't pass the flag, are bit-identical). Wired into run_ps_dtfe.sh (AVG_SUBSAMPLES=2) and reported in printOptions. The unaveraged fields are unaffected (they are always cell-centre, nSub=1).
- Memory reductions (July 2026), all validated bit-or-tolerance-identical by the test battery: each partition's triangulation is freed right after its deposit (its last read) instead of at partition scope end, so the ~0.65 KB/vertex no longer coexists with the merge phase; the GPU deposit allocates only the requested moment grids (the second-moment and gradient grids are 24+36 B/cell of sub-grid, host- and device-side) and skips extracting the per-tet velocity array on density-only runs; the mass_weight normalization grid (4 B/cell) aliases the density accumulator whenever the density field is selected; the GPU extraction cost-sort permutes its tet arrays in place (no transient gather copy); the per-partition cell-handle vector is gone (cells stream directly off the CGAL iterator). Measured on a synthetic 96^3-particle box, 256^3 grid, '--partition 2 2 2 --max-concurrent 2' (M1 Max): CPU run with density+velocity+dispersion 3.21 -> 2.77 GB peak RSS; GPU ('--ps-gpu') run with density+velocity 6.32 -> 2.89 GB.
- PS-DTFE '--partition' periodic copies are now generated PER-PARTITION on the fly (new helper findParticlesInBoxLagrangianPeriodic in subpartition.h) instead of materializing the whole-box array of Lagrangian periodic images up front. That global copy array was held resident for the ENTIRE run (originals + ~1.2x N copies, ~14 GB at 512^3) even though each partition only needs the images overlapping its own padded slab. The partition path now keeps state.particles originals-only (~6.4 GB at 512^3) and each partition synthesizes just the images whose shifted Lagrangian position lands in its padded box -- the dominant fixed memory floor under the partition loop drops by ~8 GB, which directly lets more partitions run concurrently within a given RAM budget. Bit-for-bit identical to the old global-copy path: every partition's padded box is a subset of the global padded box (lagPadding <= lagPad by construction), so the deferred image set is exactly what the global build + selection produced -- confirmed by ps_parallel_check.sh (PASS) and ps_regression_test.py (matches the stored baseline exactly). The single-triangulation (no-'--partition') PS path still builds all images up front because one global tessellation needs them; standard DTFE is unchanged (its --partition path already generated periodic copies per-partition via findParticlesInBox).

VERSION 1.2
Added some new features:
- added code for reading data from an HDF5 Gadget file

- added a new option called '--input' or '-i' that can be used to specify the input file type, the data to read from the input file and for what species. The '--input' option has the form: '--input  input_file_type   data_to_read    particle_species_to_read'   where the last two make sense only for Gadget files. The DEFAULT values are: '--input 101 7 2'
- the new option '--input' or '-i' needs to be followed by an integer specifying the input file type. By default it understands the following options: 
      101 - gadget binary snapshot saved as single or multiple files type I or II [ DEFAULT choice unsless specified otherwise in the Makefile ]
      105 - gadget HDF5 file/files
      111 - reads particles positions and masses (weights) from a text file. First line gives particle number followed by 6 coordinates giving the box dimensions: "xMin xMax yMin yMax zMin zMax". After this each row 'i' in the file gives positions X, Y, Z and weight for particle 'i'.
      112 - reads particles positions from a text file. First line gives particle number followed by 6 coordinates giving the box dimensions: "xMin xMax yMin yMax zMin zMax". After this each row 'i' in the file gives positions X, Y and Z for particle 'i'. (note that each particle is assumed to have the same mass/weight)
      121 - read particle positions, mass and velocities from a binary file. Modify this function in file 'src/io/binary_io.cc'
      131 - read particle positions, mass and velocities from your custom file. Modify this function in file 'src/io/my_io.cc'
you can set the default output file in the Makefile by changing the values assigned to the '-DINPUT_FILE_DEFAULT' option.
- added a second integer value to the '--input' option to specify what which data to read. At the moment works only for gadget files and you can select to read the following:
      1 - read particle positions
      2 - read particle weights
      4 - read particle velocities
to read multiple data add the number corresponding to each data set, for example 3=1+2 - specifies to read only particle positions and weights/masses, while a value of 7=1+2+4 specifies to read positions, weights and velocities [ DEFAULT = 7 -read positions, weights and velocities ]
- added an additional third option after for the '--input' parameter which specifies for which gadget particle species to read the data. You can select the following:
      1 - read the data for gadget species 1 (normally gas particles)
      2 - read the data for gadget species 2 (normally dark matter particles) [DEFAULT]
      4 - read the data for gadget species 3 (usually stars or different mass DM particles in multiple resolution simulations)
      8 - read the data for gadget species 4
      16 - read the data for gadget species 5
      32 - read the data for gadget species 6
to read data for multiple species just add the number corresponding to each particle type, for example 7=1+2+4 - specifies to read the data for both particle types 1, 2 and 3.

- added the '--output' or '-o' option to specify the output file type. Available options:
      101 - the default binary output
      100 - binary file with my own custom header and file structure
you can set the default output file in the Makefile by changing the values assigned to the '-DOUTPUT_FILE_DEFAULT' option.

- added option '--resdhiftSpace' that can be used to tranform the particle positions from position-space to redshift-space. For the option to work you need to enable the '-DREDSHIFT_SPACE' option in the Makefile. Than you need to call the '--resdhiftSpace d1 d2 d3' during runtime with (d1,d2,d3) the direction along which to use the velocity for the transformation to redshift space. The (d1,d2,d3) direction will be normalized to a unit vector by the program!
